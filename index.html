View Dataset ↗ Starter Repo ↗
Why this dataset fits the problem: each row already carries both the predictive signals (impressions, clicks, CTR, position, engagement, content metadata) and a ground-truth trend label derived independently from a 30-day-vs-30-day impression comparison — so the classification target isn't hand-labeled or simulated, it's measured. The 32-client spread also makes a client-holdout evaluation possible, which is what a real deployment scenario (scoring pages for a client the model has never seen) actually requires.

Data quality, honestly: missingness is structural, not random — provider_used is blank for 21,438 rows, and word_count/char_count are blank for 7,699 rows, concentrated entirely in one content type (feedly article). This was handled explicitly rather than blindly imputed — see Methodology.
02 / Research

The Problem

Problem

Manual review doesn't scale

Content teams managing large page libraries can't manually audit every page every month to catch performance decline early. Something has to do the first pass of triage.

Objective

Rank pages by decline risk

Predict is_declining_label — whether a page's impressions dropped >20% over the last 30 days vs. the prior 30 — from signals available before that comparison window closes.

Why It Matters

Decision support, not automation

A ranked, probability-scored queue lets a small team spend limited review time on the pages most likely to need it, instead of reviewing chronologically or by gut feel.

03 / Pipeline

Methodology

The actual sequence run in the notebook — nothing here is aspirational.

01

Data Collection

Load the 30,000-row anonymized starter slice of the FlyRank content-performance warehouse via the companion GitHub repo.

02

Data Cleaning

Coerce numeric columns, fill structurally-missing values (0 for numerics, "unknown" for categoricals), filter to pages with real impression history and ≥90 days of age, drop duplicate content IDs.

03

Exploratory Data Analysis

Target balance, correlation structure across 18 numeric features, decline rate by content type and freshness tier — checking for leakage and confounds before modeling.

04

Feature Engineering

Log-transform heavy-tailed traffic counts, derive engagement-quality flags, exclude trend_direction / trend_pct from features (label source — leakage otherwise).

05

Model Training

Client-holdout split (GroupShuffleSplit on client_id), then Logistic Regression, Decision Tree, and Random Forest trained on identical preprocessed features.

06

Model Evaluation

Accuracy, precision, recall, F1, ROC-AUC on the held-out clients; confusion matrix, ROC comparison, and feature importance for the selected model.

05 / Model

Model Selected

Model

Logistic Regression

Why This Model?

All three candidates landed within 2 points of F1 on this feature set — added complexity from Random Forest and Decision Tree didn't buy real separation. Logistic Regression won on F1 (64.2%) and AUC (0.616) while staying fully interpretable: every coefficient has a direct, explainable direction, which matters for a tool meant to justify its ranking to a content team.

Limitations

⚠ Read honestly
  • Modest signal: AUC ≈ 0.6 means this ranks pages better than chance, but is not a reliable individual-page verdict.
  • Teaching-scale slice: 30k rows from a ~79M-row warehouse — directional, not the full population.
  • Client imbalance: 32 clients contribute unevenly; content-type effects may be client-driven.
  • No causal claims: freshness/decline correlations are not evidence that updating a page prevents decline.
